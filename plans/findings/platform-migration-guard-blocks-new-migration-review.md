# The migration guard blocks the hand review of a just-generated migration

## Found while

Implementing identity-access/001, step 7 (migration `0003_identity_users_and_sessions.py`).

## What

- The recipe says to generate a migration and then **review it by hand**; a new module's first
  migration must gain `op.execute('CREATE SCHEMA IF NOT EXISTS "<m>"')` because autogenerate
  does not create schemas (`docs/recipes/db-change.md` step 3, `apps/api/README.md`
  "Database changes").
- `uv run just db-revision "msg"` writes the file to `apps/api/migrations/versions/`. From that
  moment `.claude/hooks/guard_paths.py:77-78` refuses any Edit/Write to it ("Existing
  migration"), because it only checks that the path exists — not whether the migration is
  committed or applied. `guard_bash` also refuses `rm` of migration files, so the generated
  file can be neither fixed nor regenerated by an agent.
- Result in this plan: the generated `0003` has no `CREATE SCHEMA "identity"`, fails on
  `just db-migrate` (rolled back; the development database stays at `0002`), and fails
  `ruff check` (two E501 lines from the autogenerated formatting), so `uv run just check` is
  red.

## Why it matters

Every new module (and any migration needing a hand edit, e.g. data steps or server defaults)
hits this. The recipe and the guard contradict each other, and an agent following both rules
must stop and hand the edit to the user.

## Suggested next step

A small platform fix: let the guard allow edits to a migration file that is untracked by git
(never committed), or have `db-revision` generate to a scratch location for review before it
lands in `versions/`. Add a hook test for "untracked new migration is editable, committed one
is not".

## Resolution (2026-10-03, fast lane, user's decision)

`.claude/hooks/guard_paths.py` now blocks a migration only when git knows it
(`git ls-files --error-unmatch`; staged counts as known), when it is a symlink, or when git
cannot answer (not a repository, git missing, timeout): fail closed. A file just generated by
`just db-revision` can be reviewed by hand, as `docs/recipes/db-change.md` step 3 asks.
Regression tests in `scripts/harness/test_hooks.py`: an untracked migration is editable and
becomes blocked once added; an untracked one outside a git repository stays blocked (the
fixture now tracks its `0001_initial.py`, like the real repo). Verified live: the guard
allowed an edit payload for the untracked `0003_identity_users_and_sessions.py` and still
refused `0002_catalog_brands.py`; the reviewed 0003 was then installed and applied.
